## Apex classes

| Class | Description |
| --- | --- |
| `AddressProofUtil` | Shared validation and configuration logic for the KYC address-proof feature. It defines the four supported proof types (Aadhaar, Passport, Voter ID, Driving Licence), the Applicant__c field that stores each proof's number, the regex pattern used to validate that number, and the file tag used when the corresponding document is uploaded. Ex_KycFormController, Ex_ApplicantUpdationFormController and Ex_ApproveApplicantChangesController all call into it so the proof-type rules live in exactly one place instead of being duplicated across those controllers. |
| `BankLetterDeletionGuard` | A guard class that protects an Application's single bank letter file once its Banking Scheme request is Pending Approval or Approved: it blocks the submitted letter from being deleted, unlinked, renamed or replaced, and blocks a second file from taking the bank-letter name while one is already on the Application. It runs without sharing and in system mode because the acting user may not otherwise have access to the Application or its files, and resolves the submitted letter via Bank_Letter_Document_Id__c rather than ContentDocumentLink visibility. |
| `BookingTaskController` | An Aura-enabled controller that creates a Task from the UI against a Booking (WhatId) and Contact (WhoId), taking subject, type, description, activity date, status and priority as parameters. It looks up the Task object's Record Types by developer name and assigns Post_Sales_Call, Presales_Call or Sales_Call based on the subject text (defaulting to Post_Sales_Call), then inserts the Task and returns its Id. Throws an AuraHandledException if no subject is supplied. |
| `BulkDemandsReceiptsDashboardController` | Backs a dashboard LWC for bulk-downloading Demand and Receipt documents and emailing them in bulk. It exposes a cacheable fetchProjects() method for populating a project picker, a DemandWrapper inner class that carries a Demand__c plus pre-formatted currency strings for the UI, and a shared buildAuraHandledException helper that explicitly calls setMessage() so error text actually reaches the LWC instead of a generic 'script-thrown exception' message. |
| `CommunitiesSelfRegController` | A classic Visualforce self-registration controller for an Experience Cloud community that allows self sign-up. It collects first name, last name, email and password fields, validates that password and confirm-password match, then calls Site.createExternalUser to provision the external user (with profile/role/account left for the implementer to fill in) and logs the user in via Site.login on success, surfacing any Site.ExternalUserCreateException messages as page errors. |
| `cpPortal_Controller` | The large, shared Aura-enabled controller behind most Channel Partner portal components: it returns the logged-in portal User, the list of active Launches eligible for the CP portal, a CP's associated launches by community username, and lookups like the launch's company name from a CP PO Line Item. Because so many CP portal LWCs call into it, it acts as the de facto data-access layer for the whole CP portal experience, running without sharing so guest/community users can read the records they need. |
| `customerPortal_CaseServices` | Creates and manages Support Cases raised from the Customer Portal. It maintains static maps translating a customer-facing L2 category (Update Profile, Payments related, Documents, Loan related, Others) into both a display label and an internal L1 category (Request/Query/Enquiry/Dispute), then createCustomerSupportCase() looks up the related Application, assigns the Case owner to the Booking's Service Manager (falling back to the Opportunity's Closing Manager), and sets origin, priority and status before inserting it. |
| `CustomerPortal_CMSLatestUpdatesCtrl` | Manages the 'Latest Updates' CMS tab, covering Newsletter and Video content plus the audience-targeting rows that decide which customers see which content. Content itself is decoupled from any Launch/Phase; instead, separate targeting rows pair a Launch and Phase (with Project derived from them) to a content item, and a customer only sees content whose targeting exactly matches their own Launch and Phase. It exposes DTOs for targeting input, project/launch/phase tree nodes, and reach (customer/investment count) estimates. |
| `CustomerPortal_KeyActionReportService` | Aggregate reporting service behind the Customer Portal's internal Key Action Report dashboard, running without sharing so an admin can see portal activity across every customer regardless of their own record access. getSummary() and related methods accept optional start/end date bounds (null meaning unbounded) and roll up stats like open vs closed Case counts, using shared status-bucket sets that mirror the logic in CustomerPortal_CaseServices, capped at a 5,000-row limit per query. |
| `CustomerPortal_KYCFormService` | Backs the Customer Portal's KYC form, covering up to five applicant slots (Primary through Fifth Applicant) with personal-details and property-details wrapper classes for the UI, plus constants for a post-submission feedback form (rating, free-text comment, 'most liked thing' questions) that is fired once a customer finishes the KYC flow, tagging form submissions as coming from the Customer Portal. |
| `DocumentGenerationServices` | A broad document-generation utility, originally built for an Exceller demo org, that dynamically describes Applicant__c's full field set and queries every field for the primary (or all) applicants on a given Booking using Database.query() with a string-built SOQL statement — used as a data source for generating letters, receipts and other customer-facing documents without hardcoding each field name. |
| `Ex_AmountOverDueBatchClass` | A combined Batchable/Schedulable class that scans for payment milestones or demands overdue by a configured window (built around a 'today minus 5 days' / 'three days ago' cutoff) and sends reminder emails to the relevant service manager and booking contact, with Database.AllowsCallouts enabled so the batch can also make external callouts as part of the overdue-notification process. |
| `Ex_ApexSharingManagementServices` | The org's central Apex-managed sharing utility, used by multiple trigger handlers (Applicant, Application) to share Leads, Opportunities and custom objects with specific users or teams outside standard role-hierarchy visibility. shareRecordWithTeamLeadandTeamHead() dynamically builds the correct share-object and parent-field names per SObject type (LeadShare/OpportunityShare/__Share), queries existing shares to avoid duplicate inserts, then shares each record with the mapped team leads and heads. |
| `Ex_AppCancellationDocVerifierController` | Updates an Application's bank account details (name, number, branch, IFSC code, bank name) when a refund's cancellation documentation is being verified, looking up the parent Application from the given Refund__c record and only overwriting fields the caller actually supplied, throwing an AuraHandledException if the refund Id is missing or invalid. |
| `Ex_ApplicantUpdationFormController` | Backs the applicant-updation screen on a Booking. isIndividualOrCompany() reports whether the booking's Application is for an individual applicant type, and getApplicantsForBooking() returns every applicant on the booking with a very large field set — full address (current and alternate), identity documents (PAN, Aadhaar, passport, voter ID, driving licence), occupation/profession, marital status, spouse details and up to ten children's names and dates of birth — ordered by applicant type for the update form. |
| `Ex_ApplicationCancellationCaseController` | Supports the Application-cancellation Case workflow. getCase() returns a Case's approver comments at each escalation level, its escalation level and assignee, and the related Application, while getFirstRefundDeskUserId() finds the longest-tenured active user on the 'Refund Desk' profile to use as a default assignee when a cancellation case needs to be routed to that queue. |
| `Ex_ApplicationCancelMessagingBatch` | A scheduled Batchable job that finds every open Case flagged as an Application-cancellation refund case and gathers each one's full escalation contact chain — the application owner, the closing manager's team lead, the launch's closing head, business head, MSS lead/head and CSO, plus the project's refund helpdesk team — together with aging fields (hours open, response/escalation TAT) so the paired handler class can send the right overdue-escalation emails to the right people. |
| `Ex_ApplicationCancelMessagingHandler` | Sends escalation emails for aging Application-cancellation cases found by Ex_ApplicationCancelMessagingBatch. It defines business-hours (9) vs calendar-hours (24) constants for SLA math, builds a clean manager display name from first/last name fields (falling back gracefully if either is blank), and groups cases by escalation day-number and manager name so one combined email per manager/day can be sent instead of one per case. |
| `Ex_ApproveApplicantChangesController` | Backs the approval screen for applicant-detail change requests raised as a Task. getTaskComments() returns a Task's subject, description, created date and approval status, getRecordOwnerId() looks up who the Task is currently assigned to (for comparing against the logged-in user), and processApplicantChanges() applies the proposed applicant field changes (passed as JSON) once a manager approves or rejects them. |
| `Ex_BookingHandlerServices` | A large service class holding core Booking__c business logic, including (in code beyond this excerpt) demand-raising based on payment milestone schedules. Its commented-out raiseBookingRelatedDemand() method shows the intended approach: dynamically build a SOQL query across Payment_Milestone__c's full charge breakdown (agreement value, development/consideration/statutory/other charges with GST splits) for bookings due on calculated demand-raise dates, tying milestones back to their Quotation and correspondence contact. |
| `Ex_BookingTriggerHandler` | The handler behind the Booking__c trigger, covering a wide range of post-booking automation on insert: grouping bookings by Campaign for campaign-performance updates, collecting bookings tied to a CP Launch for channel-partner processing, and (per its header comments) previously also auto-created Registration Cases and ran round-robin Key Account/Collection Manager assignment, both since commented out and left disabled. |
| `Ex_BulkDocumentController` | Backs a bulk-document-generation dashboard covering pre-possession intimation letters and statements of account. getPhaseList() dynamically queries RERA_Phase__c (or an equivalent phase object) scoped to a Project, and getProjectList() dynamically describes Project__c to build a full field list at runtime; document generation is gated by constants requiring the booking to be in Booking Confirmed, Booking Completed or Booking Retention In-Process for a Statement of Account to be produced. |
| `Ex_CallDispositionController` | Backs the call-disposition logging UI used after a sales call. getCategoryPicklist() reflects Task.Category__c's active values for the disposition category dropdown, and getActiveLaunches() returns every active Launch (enforcing field-level security) as label/value options so the agent can tag which launch the call related to. |
| `Ex_CampaignHandlerServices` | Creates Campaign_Performance__c tracking records for a given set of Campaign Ids. For 'Daily' performance type it inserts one row dated today per campaign; for 'One-Time' type it instead dates the row to the campaign's own StartDate, giving campaigns that only run once a single performance record tied to their actual run date rather than a recurring daily one. |
| `Ex_CaseAgeBatch` | A scheduled batch, built around a hardcoded 2017 cutoff date, that re-queries every open Case (status not Closed) with its full escalation chain (three escalation levels, their TATs and emails, team leader) and recalculates each case's Age_In_Hours__c against HoABL's configured Business Hours, sending notification emails and a custom notification to the case owner as cases cross their response/escalation thresholds. |
| `Ex_CaseAndTaskManagement` | Backs a combined case/task timeline component shown on a Booking or an Account (rolling up every booking under that account). getRecords() fetches every Case tied to the relevant booking(s) with its escalation chain and categorization fields, grouping parent cases and their child cases into wrapper objects so the UI can render a nested case tree per booking. |
| `Ex_caseEscalationMonitorController` | Backs a Case Escalation Monitor component. escalationDetails() returns an open case's full escalation state (age in hours, three escalation levels with names/TATs/timestamps, customer tier), and getAdjustedBusinessHoursEndTime() calculates when a TAT actually expires by adding the given number of hours to a start time using HoABL's configured Business Hours rather than naive calendar time. |
| `Ex_CaseHandlerServices` | A future, callout-enabled method that back-fills a Case's Account, Booking and Application from related records once a case is created, tagging the Account if it was left null. It resolves a default routing user from Case_Management_Default_User__c (matching the admin username with a LIKE pattern so sandbox-suffixed usernames like 'salesforceadmin@force.com.uat' still resolve) and uses that as a fallback owner when no project-specific routing applies. |
| `Ex_CaseTrigger` | The Case trigger (after insert, before/after update) that delegates to Ex_CaseTriggerHandler's afterInsert, beforeUpdate and afterUpdate methods; a before-insert hook exists in the handler but is currently commented out of the trigger body. |
| `Ex_CaseTriggerHandler` | Handles Case trigger logic, including (per this excerpt's afterInsert) loading configured restricted email domains from Case_Domain_Restrictions__c to flag or filter cases whose SuppliedEmail comes from a blocked domain — the actual case-deletion logic for matched domains is currently commented out, leaving the restricted-domain list collected but not yet acted upon in this version. |
| `Ex_CemWiseReportDashboardCtrl` | Powers the CEM-wise Report and KPI tiles on the Customer Service Dashboard. Every query is scoped by GROUP BY on (CEM, Project) pairs or bounded Task/date windows to stay performant regardless of record volume, using carefully confirmed field choices documented inline — e.g. summing Booking__c.Net_Booking_Amount__c rather than Total_Agreement_Value__c (unused), classifying SLA breaches by a non-null Escalation_Level__c, and excluding the ~77% of Cases with no Booking__c since they can't be attributed to a CEM. |
| `Ex_ClickToCallController` | Supplies picklist options for the click-to-call dialog on a Task: getCategoryPicklist() reflects Task.Category__c's active values and getFundingTypePicklist() reflects Task.Funding_Type__c's, letting the LWC populate both dropdowns from live schema metadata instead of a hardcoded list that could drift from the actual picklist configuration. |

| `Ex_CPPOManagementServices` | Determines AOP (Annual Operating Plan) brokerage eligibility for Channel Partners on new Bookings. checkForAOPLaunchBrokerage() collects each booking's Channel Partner, booking date and Launch, resolves which AOP Brokerage Plan is active for each booking date, then checks which of those Channel Partners are registered as eligible AOP partners for that plan before applying the special AOP brokerage calculation instead of standard brokerage. |
| `Ex_CPRegistrationFormController` | A global, without-sharing controller for the public CP (Channel Partner) Registration Form. getCountryCodes() returns every configured Country_Codes__c record but pulls India out to the front of the list (as the most common choice) ahead of all other countries, giving the public-facing registration form a sensible default-first country-code picker. |

| `Ex_CTIDashboard` | Filters and prepares Leads before they're uploaded to the Convox CTI partner. getCustomSettings() returns the configured Convox_CRM_Fields__c mappings, deliberately excluding a fixed set of fields (project/launch name, proposed VC date/time, sourcing manager, UTM fields, name/email, customer rating) that are handled separately, and getPicklistValues() generically reflects any Lead field's picklist values for the dashboard's filter controls. |

| `Ex_CustomActivitiesController` | Backs the ex_customActivities LWC, which shows a Booking's related Tasks and Events as a unified activity timeline. | `Ex_CustomerTierApprovalController` | Backs the customer-tier approval queue, where a proposed tier change for an Account sits as a Post_Sales_Call Task pending manager sign-off. getPendingCustomerTierApprovals() returns each pending approval as a CustomerTierApprovalRow carrying the account, the metrics driving the proposed tier (portfolio value, unit count, referral count, overdue ratio), and the task's creation date for the approver to review before approving or rejecting. |

| `ex_customTaskController` | Backs a custom task-creation component (closely mirroring ex_convoxtaskdisportionController). getRecordTypeId() resolves the Task record type Id for 'Sales Call', and an ObjectInfoResponse wrapper reports whether a given object is a Lead so the component can adjust its field layout for Lead vs other object types. |
