## Apex classes

| Class | Description |
| --- | --- |
| `CustomerPortal_MilestoneServices` | Computes the ownership-journey milestones shown to a logged-in customer across all their Applications. getMilestones() pulls each Application together with booking-level checklist flags (DOC registration, possession readiness, AFS registration, balance-due and no-due checklists, KYC submission) and maps them through static milestone-name and milestone-label mappings built once in a static initializer, returning a per-Application ordered list of milestone DTOs for the portal's journey timeline component. |
| `DocumentGenerationServices` | A broad document-generation utility, originally built for an Exceller demo org, that dynamically describes Applicant__c's full field set and queries every field for the primary (or all) applicants on a given Booking using Database.query() with a string-built SOQL statement — used as a data source for generating letters, receipts and other customer-facing documents without hardcoding each field name. |
| `Ex_AggrravatedCustApprovalController` | Supports an 'aggravated customer' refund-approval flow: getRefundDetails() returns a Refund__c's category, forfeiture/refund amounts, due date and up to three named approvers, while sendAggravatedCustomerRequestForApproval() marks the refund Pending For Approval, records the requested number of days to reduce, and threads the related Booking/Project/Launch context into the submission. |
| `Ex_AppCancellationDocVerifierController` | Updates an Application's bank account details (name, number, branch, IFSC code, bank name) when a refund's cancellation documentation is being verified, looking up the parent Application from the given Refund__c record and only overwriting fields the caller actually supplied, throwing an AuraHandledException if the refund Id is missing or invalid. |
| `Ex_ApplicationCancellationCaseController` | Supports the Application-cancellation Case workflow. getCase() returns a Case's approver comments at each escalation level, its escalation level and assignee, and the related Application, while getFirstRefundDeskUserId() finds the longest-tenured active user on the 'Refund Desk' profile to use as a default assignee when a cancellation case needs to be routed to that queue. |
| `Ex_ApplicationCancelMessagingHandler` | Sends escalation emails for aging Application-cancellation cases found by Ex_ApplicationCancelMessagingBatch. It defines business-hours (9) vs calendar-hours (24) constants for SLA math, builds a clean manager display name from first/last name fields (falling back gracefully if either is blank), and groups cases by escalation day-number and manager name so one combined email per manager/day can be sent instead of one per case. |
| `Ex_ApplicationHandlerServices` | Houses Application__c business logic, with sortApplicationsSequenceWise() as a @future method that reloads a given set of Applications ordered by creation date, groups them by their parent Opportunity, and (in code beyond this excerpt) renumbers each Opportunity's Applications' Sequence__c so applications are always numbered in the order they were actually created, even after some are deleted or reordered. |
| `Ex_bookingCancellationController` | Reverses a booking cancellation in progress: updateBookingStatus() resets a Booking__c back to 'Booking Confirmed' and nulls out every cancellation-related field (status, initiator, reason/sub-reason, liquidated and brokerage charges, interest amount, promoter-borne costs and taxes, refund amount), effectively undoing a cancellation request so the booking returns to its normal active state. |
| `Ex_BookingHandlerServices` | A large service class holding core Booking__c business logic, including (in code beyond this excerpt) demand-raising based on payment milestone schedules. Its commented-out raiseBookingRelatedDemand() method shows the intended approach: dynamically build a SOQL query across Payment_Milestone__c's full charge breakdown (agreement value, development/consideration/statutory/other charges with GST splits) for bookings due on calculated demand-raise dates, tying milestones back to their Quotation and correspondence contact. |
| `Ex_CemWiseReportDashboardCtrl` | Powers the CEM-wise Report and KPI tiles on the Customer Service Dashboard. Every query is scoped by GROUP BY on (CEM, Project) pairs or bounded Task/date windows to stay performant regardless of record volume, using carefully confirmed field choices documented inline — e.g. summing Booking__c.Net_Booking_Amount__c rather than Total_Agreement_Value__c (unused), classifying SLA breaches by a non-null Escalation_Level__c, and excluding the ~77% of Cases with no Booking__c since they can't be attributed to a CEM. |
| `Ex_CollectionSummaryDashboardCtrl` | Powers the Collection Summary panel of the Customer Service Dashboard with a two-tier drill-down: tier one (getCollectionSummaryByProject) groups by Project only, so it's always bounded by project count; tier two (getCollectionSummaryByBooking) groups by Booking but only within one selected project and paginates with a LIMIT + Id cursor, so expanding a project never loads more than one page regardless of how many bookings it has. Figures are deliberately sourced from Demand__c.Total_Amount_Demanded__c/Total_Amount_Remaining__c and Receipt__c.Approval_Status__c = 'Approved' rather than Agreement/Consideration Value fields, which the class's own comments note are mirrored duplicates in this org and would double-count if summed. |
| `Ex_ContentDocumentLinkTriggerHandler` | On file-attachment insert, renames the newly linked file's latest ContentVersion with a suffix identifying its purpose based on what it's attached to: '- Signed AFS' for files linked to a Scheduled_Registration_Slot__c, '- Challan' for files linked to a Registration_Case__c, and (for Channel Partner or Knowledge Hub Manual attachments) separately tracks the link for further processing not shown in this excerpt. |
| `Ex_CustomerServiceDashboardCtrl` | Supplies the filter-bar dropdown options (CEM, Project, Booking Stage) shared across every panel of the Customer Service Dashboard shell, which resolves an 'All X' selection into the full explicit option list before calling each panel so every panel's query always receives a concrete IN-list. It defines which profiles count as CEM-tier (Service/Registration Managers and TLs, CSS leadership and MIS variants, including 'Vertical -' prefixed role variants that an earlier version silently excluded) versus which profiles see every panel unfiltered (System Administrator, Tech MIS). |
| `Ex_DocumentDispatchController` | Backs the Document Dispatch Information LWC on a Registration Case, which tracks the full lifecycle of a physically signed document: signing date, dispatch date/mode, courier company and tracking number, delivery date, return handling (whether returned, to whom, and why) and final handover (to whom and when). getRegistrationCase() loads all of this as a RegistrationCaseWrapper, replacing an earlier version that returned the raw Registration_Case__c record directly. |
| `Ex_DocumentHandoverController` | Backs the Document Handover action on a Registration Case. submitDocumentHandover() records the full handover event — document status, handover date, courier tracking number, address confirmation, whether customer acknowledgement is available, handover type, and up to two uploaded files (the handover document and the customer acknowledgement) — updating the Registration Case's status and handed-over flag accordingly. |
| `Ex_FinanceTeamRefundDashboardController` | Backs the Finance team's refund dashboard. getRefundStatusList() reflects Case.Application_Case_Status__c's picklist values but explicitly excludes 'Sales Retention In-process' and 'Pending MSS Approval' from the filter options (since those statuses aren't relevant to Finance's refund queue), and getRefundList() returns the actual paginated list of refund cases matching the dashboard's selected filters. |
| `Ex_InitiateBookingCancellationController` | Backs the booking-cancellation initiation screen. getBooking() returns a Booking's correspondence contact, service manager, outstanding amount and interest, the project's interest rate/SBI MCLR, and the full history of up to ten numbered interest letters (each with its own sent flag and sent date) and two interest notices, giving the cancellation flow full visibility into every interest communication already sent before initiating cancellation. |
| `Ex_IVRDashboard` | Backs an IVR-related dashboard. getRegistrationCaseTypeForBooking() returns the registration types of every Registration Case tied to a Booking (or a placeholder message if no booking is given), and getBookingsByAccount() returns the Bookings under a given Account, letting an IVR agent or automated call flow look up a customer's registration status and bookings by account. |
| `Ex_PrebookingCancellationController` | Supports the pre-booking cancellation OTP flow, which verifies the customer via a Salesforce Marketing Cloud OTP journey. getEventDefinitionKey() looks up the 'Cancellation OTP' record in Marketing_Cloud_client_creds__c to get the Journey Builder event-definition key needed to trigger that journey, and getFilesForRecord() returns the ContentVersions attached to a given Application for the cancellation screen to display. |
| `Ex_PrePossessionCalculator` | Computes the data shown on a pre-possession summary for a Booking. calculate() resolves the project/RERA phase/unit names, plot size, and whether the unit's most recent Registration Case is Closed (mapped to a simple 'Registered'/'Unregistered' status), plus the primary and co-applicant names from the booking's Applicants, assembling it all into a single string-keyed map for the pre-possession display or letter template. |
| `Ex_PreTerminationController` | A Visualforce controller for the pre-termination letter, reusing the same Milestone-list and running-totals pattern as the interest letter controllers, plus property/location fields (village, district, taluka, plot number, project) and applicant contact details, so the page can render a full pre-termination notice showing both the overdue milestone breakdown and the property/customer context. |
| `Ex_ReceiptHandlerServices` | Tags each Receipt with the correct Company Bank Account for reconciliation. tagCompanyAccountOnReceipt() resolves each receipt's Booking's Company, then looks up that company's Company Bank Account records, giving the receipt handler (beyond this excerpt) the information needed to automatically associate a payment with the right legal entity's bank account rather than requiring manual selection. |
| `Ex_ReceiptTriggerHandler` | On Receipt insert, builds several parallel maps grouping new receipts by their parent Application, Booking, and whether they represent on-account money, plus tracking which bookings need Apex sharing extended to cover the new receipts and which receipts came through a Bank Transaction — feeding each group into its own downstream processing (ledger updates, booking total recalculation, sharing) rather than a single monolithic routine. |
| `Ex_RefundHandlerServices` | Assigns escalation approvers for refunds flagged under the 'Aggravated' customer category. assignApproversForAggravatedCustomer() resolves each affected Booking's Project and that project's CSS Team Leader (and separately the Launch's CEO), building the approval chain so an aggravated-customer refund is automatically routed to the right senior approvers rather than a standard refund approver. |
| `Ex_RefundHelpdeskDashboardController` | Backs the Refund Helpdesk dashboard's paginated, sortable refund list. getRefundList() validates the requested sort field against an explicit allow-list (refund name, applicant name, application name, case number, refund amount, due date, document-verified flag, launch name), defaulting to due-date order, before returning the page of refunds matching the requested status. |
| `Ex_RefundTrigger` | The Refund__c trigger (before insert, after insert, after update) routing to Ex_RefundTriggerHandler's beforeInsert, afterInsert and afterUpdate methods. |
| `Ex_RefundTriggerHandler` | On Refund before-insert, groups new refunds tied to a Booking with Customer_Category__c = 'Aggravated' by their Booking Id, intending to call Ex_RefundHandlerServices.assignApproversForAggravatedCustomer() for the group — that call is currently commented out, so the escalated-approver assignment for aggravated-customer refunds is presently disabled at the trigger level even though the underlying service method still exists. |
| `Ex_RegCaseApprovalController` | Submits a Registration Case for finance/TL approval. submitApproval() validates the record Id, loads the case's current Finance and TL approval status along with whether it's being processed without a challan, then conditionally updates the challan type, mode and account fields supplied before routing the case into the approval process. |
| `Ex_RegCaseStatusDashboardCtrl` | Powers the Registration Case Status panel of the Customer Service Dashboard with the same two-tier pattern as the Collection Summary panel: getRegistrationCaseStatus() aggregates case and slot counts GROUP BY Project only (bounded by project count), while getRegistrationCaseByBooking() paginates a booking-level drill-down for one project at a time. The date filter only scopes which Registration Cases count toward the totals — booking pagination itself is ungated by date, with bookings that have no cases in the selected range sorted to the bottom showing zeroes. |
| `Ex_RegistrationApprovalConfirmationPopup` | Submits a Registration Case for approval. sendRegistrationForApproval() loads the case's current approval status and Service Manager, fires a 'Notification_to_Registration_owner' custom notification to that manager naming the case as awaiting their review, and (beyond this excerpt) updates the case's approval status to 'Requested for Approval'. |
| `Ex_RegistrationBatchClass` | A callout-enabled batch sending follow-up communication 15 days after a registration intimation letter was sent, for cases where the SDR (stamp duty & registration) fee hasn't been paid yet. It classifies the booking's project type into plot/unit/villa terminology and sends from the 'My Land' Org-Wide Email Address with the booking's charge-detail/amount breakdown (up to 5 charge lines) for the customer to review. |
| `Ex_RegistrationCaseController` | Backs a Registration Case detail component. Its BookingDetailsWrapper bundles the booking name, customer name/email/contact, booking stage and whether AFS (Agreement for Sale) is deferred into a single DTO so the registration screen can show the relevant booking context for the case being processed. |
| `Ex_RegistrationCaseHandler` | On Registration Case before-insert, collects the parent Bookings and resolves each one's Quotation, SDR payer, Service Manager, the project's Registration Team Lead and Accounts Manager, building the context needed (processed further beyond this excerpt) to correctly populate ownership, approver and charge fields on the new registration case. |
| `Ex_RegistrationCaseHandlerServices` | Processes the per-registration-case charge breakdown. processChargeDetails() fetches each relevant Quotation's Statutory and Other Charges that are specifically payable 'at the time of Registration', groups them by Quotation, and cross-references applied discounts so the registration case's charge fields reflect exactly what the customer owes at registration, net of any discounts. |
| `Ex_RegistrationCaseTrigger` | The Registration_Case__c trigger (before/after insert and update) routing to Ex_RegistrationCaseHandler's four lifecycle methods, with an after-update branch added specifically to fix demands not being raised when a case became 'Is Due for Registration Linked'. |
| `Ex_RegistrationReminder1BatchClass` | A callout-enabled batch sending the first registration payment reminder, 7 days after the intimation letter, to non-legacy bookings that haven't paid SDR yet, pulling in the Key Account Manager and Service Manager's contact details plus up to 5 charge-detail lines so the reminder shows exactly what's still owed and to whom it should be addressed. |
| `Ex_RegistrationReminder2BatchClass` | A callout-enabled batch sending the second registration reminder, 15 days after the first reminder was sent (and only once, matched by exact date), to still-unpaid non-legacy registration cases, carrying the same KAM/Service Manager and project context as the first reminder for the follow-up communication. |
| `Ex_RegistrationReminder3BatchClass` | A callout-enabled batch sending the third and final registration reminder 15 days after the second, choosing the sender address based on project type — the standard 'My Land' address, or 'Vertical No reply' for Vertical projects — and including the case's attached Documents for reference in the final follow-up before escalation. |
| `Ex_RESTCustomerIdentityAPI` | An inbound, without-sharing @RestResource endpoint (/CustomerIdentity/*) that verifies a customer's identity by mobile number. checkMobileNumber() strips non-numeric characters from the submitted number and searches Applicant__c records where it matches either the primary or alternate mobile field, returning a 400 if no mobile number was supplied, used by an external system to confirm whether a given phone number belongs to a known HoABL customer. |
| `Ex_ScheduledSlotHandlerServices` | Keeps a Registration Case's slot-scheduled flag accurate. updateRegistrationCase() builds Registration Case updates from a list of Scheduled Registration Slots, clearing Slot_Scheduled__c back to false specifically when a slot's approval status is 'Rejected', so a rejected slot doesn't leave the case incorrectly showing a slot as still scheduled. |
| `Ex_ScheduledSlotTriggerHandler` | Handles Scheduled Registration Slot automation. afterInsert() references a 'ScheduledSlotEvent' PushTopic for real-time UI updates, and afterUpdate() (together with processApprovalStatus(), added later) detects relevant field changes and submits the slot into an approval process via Approval.ProcessSubmitRequest when appropriate. |
| `Ex_SDRChecklistController` | Backs the SDR (stamp duty & registration) Checklist component. returnMasterChecklistRecords() returns the master document checklist configured for the Registration Case's Project and Registration Type, ordered by sequence, and getCustomerDetails() returns the customer context needed alongside the checklist for the registration team to verify documents against. |
| `Ex_sendDOCReminderEmailBatch` | A scheduled, callout-enabled batch sending Direct DOC (Deed of Conveyance) reminder emails every Monday. Per its own changelog it was updated to query from Registration Case rather than Booking directly, and its commented-out query shows it originally selected nearly every field on Booking__c — reflecting how broad and long-lived this particular reminder's data needs grew before being narrowed. |
| `Ex_SendIntimationEmailHandler` | Sends the intimation email when a Registration Case is created. Its TableRow helper and formatCurrency() method build a dynamic, INR-formatted charge breakdown table (what's owed, the amount, and which account it should be paid into) for the email body, including the KYC form link as of a later update. |
| `Ex_SendIntimationEmailTrigger` | The Registration_Case__c trigger (after insert) that collects every newly inserted case's Id and re-queries it with its full charge, approval, courier and document-handling field set before handing off to Ex_SendIntimationEmailHandler to compose and send the intimation email. |
| `Ex_SendRegistrationEmailController` | Sends the registration completion email, reusing the same dynamic TableRow/formatCurrency pattern as Ex_SendIntimationEmailHandler to present a clear, INR-formatted breakdown of registration-related charges and the accounts they were paid into. |
| `Ex_SlotBookingController` | Backs the Registration slot booking dashboard. getRegistrationOffice() resolves a Booking's Project and collects up to three configured Registration Offices (Registration_Office_1/2/3__c) into a list, giving the customer a choice of registration office options tied to their specific project. |
| `Ex_WordDocumentPreviewController` | Supports previewing generated documents (reused from an Exceller demo org). getAllotmentLetterCreated() and getCSSChecklistDone() are simple boolean lookups on a Booking that gate whether certain document-preview or checklist-dependent UI elements should be shown, used as quick pre-conditions before offering a document preview. |
