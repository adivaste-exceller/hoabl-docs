## Apex classes

| Class | Description |
| --- | --- |
| `cpPortal_Controller` | The large, shared Aura-enabled controller behind most Channel Partner portal components: it returns the logged-in portal User, the list of active Launches eligible for the CP portal, a CP's associated launches by community username, and lookups like the launch's company name from a CP PO Line Item. Because so many CP portal LWCs call into it, it acts as the de facto data-access layer for the whole CP portal experience, running without sharing so guest/community users can read the records they need. |
| `CpPortal_HomePage` | An earlier or parallel controller for the CP portal home page, overlapping heavily with cpPortal_Controller: it returns the logged-in User, the full list of Launches with their portal creative/URL fields, and the Launches associated with a Channel Partner looked up by community username. Its simpler, unscoped queries (no active/test-record filtering) suggest it predates the more defensive logic later added to cpPortal_Controller. |
| `CustomerPortal_KYCFormService` | Backs the Customer Portal's KYC form, covering up to five applicant slots (Primary through Fifth Applicant) with personal-details and property-details wrapper classes for the UI, plus constants for a post-submission feedback form (rating, free-text comment, 'most liked thing' questions) that is fired once a customer finishes the KYC flow, tagging form submissions as coming from the Customer Portal. |
| `Ex_AOP_Channel_PartnerTriggerHandler` | Validates AOP_Channel_Partner__c records to prevent duplicate Channel-Partner-to-Brokerage-Plan pairings. It builds a key from each new record's AOP_Brokerage_Plan__c and Channel_Partner__c Ids, tracks keys already seen within the same transaction in a set, and adds a validation error to any record that repeats a plan/partner combination already present in the same save. |
| `Ex_AOPBrokerageCreationDashboard` | Backs a dashboard for creating AOP (Annual Operating Plan) Brokerage Slabs from an AOP Brokerage Plan. getAOPBrokerage() loads the plan's active flag, name and start/end dates, and getWrapper() seeds a list of AOPSlabWrapper rows (starting with a fixed 'Min Booking Amount' slab from 0 to 0 Cr) for the admin to adjust booking-amount brokerage tiers before saving the full slab structure. |
| `Ex_ApexSharingManagementServices` | The org's central Apex-managed sharing utility, used by multiple trigger handlers (Applicant, Application) to share Leads, Opportunities and custom objects with specific users or teams outside standard role-hierarchy visibility. shareRecordWithTeamLeadandTeamHead() dynamically builds the correct share-object and parent-field names per SObject type (LeadShare/OpportunityShare/__Share), queries existing shares to avoid duplicate inserts, then shares each record with the mapped team leads and heads. |
| `Ex_ApplicationTriggerHandler` | Handles Application__c trigger logic. | `Ex_AwekeningFormController` | Backs the 'Awakening' CP form shown at a launch. getCPLaunches() resolves a specific CP_Launch__c record by Id, and getFormQuestions() returns every Form_Questions__c configured for that launch (question text, type, and picklist options where applicable) so the form can be rendered dynamically from configured questions rather than hardcoded fields. |
| `Ex_BatchUpdateOpportunities` | A scheduled batch that walks back Opportunities sitting in 'Ready for Meeting' (or later stages flagged Re_Meeting__c) that have no linked, created Event with a Meeting__c set. For each such stale Opportunity it resets the stage to '02 - In Follow-up' with sub-stage 'Cold' and reason 'No commitment on time', effectively auto-demoting opportunities whose scheduled meeting never actually got booked as a calendar Event. |
| `Ex_BookingHandlerServices` | A large service class holding core Booking__c business logic, including (in code beyond this excerpt) demand-raising based on payment milestone schedules. Its commented-out raiseBookingRelatedDemand() method shows the intended approach: dynamically build a SOQL query across Payment_Milestone__c's full charge breakdown (agreement value, development/consideration/statutory/other charges with GST splits) for bookings due on calculated demand-raise dates, tying milestones back to their Quotation and correspondence contact. |
| `Ex_BookingTrigger` | The Booking__c trigger (before/after insert and update) that routes to Ex_BookingTriggerHandler's matching methods — afterInsert, beforeUpdate, handleBeforeInsert, beforeInsert and afterUpdate — centralizing all booking record-level automation behind a single handler class rather than embedding logic in the trigger body itself. |

| `Ex_BrokerageApprovalDashboardController` | Backs the brokerage approval dashboard, which can be opened either directly on a Launch or from an approval ProcessInstanceWorkitem. getRelatedRecords() resolves the real target Launch either way (unwrapping the approval work item's TargetObjectId if needed), validates it is actually a Launch__c, then returns that launch's Brokerage Slabs (ordered by booking-count tier) and related Spot Brokerages for the approver to review together. |
| `Ex_CampaignHandlerServices` | Creates Campaign_Performance__c tracking records for a given set of Campaign Ids.
